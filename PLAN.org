* 배경
- LLM Agent는 업무 자동화에 유용하지만, 환각과 프롬프트 인젝션 때문에 신뢰할 수 있는 실행 주체로 간주하지 않는다.
- 여러 모델과 도구를 조합할수록 데이터가 어디로 전달되고 어떤 권한으로 동작하는지 통제하는 것이 중요해진다.
- 특히 Cloud 모델에 입력을 보내는 행위 자체가 외부로 데이터를 전달하는 I/O이다.

* 프로젝트의 목적
- 스크립팅 가능한 멀티모델 오케스트레이터를 만든다.
- 새로운 DSL이나 사용자 워크플로 전체에 대한 정적 타입 증명보다, 모든 정보 전달과 외부 동작을 중재하는 코어가 중심이다.
- 모델이 공격자의 지시를 따르더라도, 명시적으로 부여된 정보 접근 및 행동 권한을 넘지 못하게 한다.

** 정보 접근 통제
- 이 정보를 이 모델에게 전달해도 되는가?
- 데이터의 보안 레벨, 출처, 목적지 및 수신 주체의 접근 정책을 검사한다.
- 최초 프롬프트뿐 아니라 도구 실행 결과와 Worker 간 전달도 검사 대상이다.
- 파일 읽기 동작이 허용되어도, 읽은 내용을 해당 모델에게 전달하는 것이 허용된다는 뜻은 아니다.

** 행동 권한 통제
- 이 모델이 요청한 동작을 실행해 줘도 되는가?
- 요청 주체, 동작 종류, 대상 자원, 인자 및 부여된 권한을 검사한다.
- 파일, 네트워크, 프로세스, 서비스 API, 모델 호출 및 Worker 간 호출을 포함한다.

* 책임의 분리
** 사용자 스크립트
- 모델 선택, 작업 연결, 분기, 반복 및 전체 워크플로를 구성한다.
- 별도 프롬프트와 검증 모델을 사용하는 내용 검증·승인 플로우도 스크립팅으로 구성할 수 있다.
- LLM 기반 검증은 코어의 권한 검사나 실행 격리를 대체하지 않는다.
- 작업을 조합하는 권한과 정책을 변경하거나 권한을 부여하는 관리 권한은 구분한다.

** 오케스트레이터 코어
- 모든 관리 대상 I/O 요청을 수신하고 정책에 따라 허용 또는 거부한다.
- 요청자의 신원과 권한은 모델의 자기 선언이 아니라 등록된 실행 세션을 기준으로 관리한다.
- 필요한 정책 정보가 없거나 명시적으로 허용되지 않은 요청은 기본적으로 거부한다.
- 허용된 요청만 실행기에 전달하고, 결과를 모델에 전달하기 전에도 정보 접근 정책을 검사한다.
- 정책 판단 이유와 실행 결과를 기록한다.

** 결정론적 어댑터와 실행기
- 구조화된 요청의 의미를 코드로 구현한다.
- 모델이 제안한 자연어를 임의의 권한 있는 명령으로 해석하지 않는다.
- 서비스 인증 정보는 코어 또는 어댑터가 관리하고, 모델에 불필요하게 전달하지 않는다.

* Worker 모델
- ~github_worker~, ~search_worker~, ~discord_worker~ 처럼 기능과 권한에 따라 실행 단위를 나눈다.
- Worker는 단순히 도구를 가진 모델이 아니라 다음을 묶은 단위이다.
  - 허용된 입력·출력 스키마
  - 요청을 처리하는 결정론적 코드
  - 모델에 전달할 데이터 구성
  - 모델 및 접근·실행 정책
- 권한은 단순 서비스 접근 여부가 아니라 서비스, 계정·자원 범위, 허용 동작 단위로 제한한다.
- Worker 간 호출도 정책 검사 대상이며, 다른 Worker를 호출한다고 그 Worker의 권한을 자동으로 획득하지 않는다.

** 구조화된 통신
- Worker 간 통신은 자유 형식 명령 문자열이 아니라, 수신 Worker의 기능에 대응하는 타입과 직렬화 스키마로 제한한다.
- 직렬화 자체가 보안을 보장하지는 않는다. 코어가 스키마, 인자, 대상 자원과 호출 권한을 검증해야 한다.
- 문자열 필드의 내용은 데이터로 취급하며, 그 내용이 새로운 권한이나 실행 명령으로 승격되지 않게 한다.
- 구조화된 데이터에도 악성 내용이 포함될 수 있으므로, 타입 검증과 내용의 신뢰성은 구분한다.

** 예: GitHub 이슈 조회
#+BEGIN_EXAMPLE
ReadIssue { repository, issue_number }
    → 코어의 호출 권한·자원 범위 검사
    → 결정론적 GitHub 어댑터가 이슈 조회
    → 조회 결과의 정보 접근 검사
    → 정해진 형식으로 모델 입력 구성
    → 모델의 분석·응답 생성
#+END_EXAMPLE
- 모델에 이슈를 알아서 찾으라고 지시하고 임의의 ~web_fetch~ 권한을 주는 구조가 아니다.
- 추가 정보가 필요하면 모델은 구조화된 요청을 제안하고, 코어가 다시 검사·실행한다.

* 정책과 데이터 표현
- 보안 레벨은 우선 ~Public / Private / Secret~을 나타내는 일반 variant로 표현하는 방향을 사용한다.
- 모든 흐름 위반을 컴파일 오류로 만드는 것보다, 정책 경계에서 각 레벨을 명시적으로 처리하고 런타임에 허용·거부하는 것을 우선한다.
- 패턴 매칭의 누락 검사는 정책 처리를 돕지만, 각 분기의 정책이 올바르다는 보증은 아니다.
- 데이터의 출처와 보안 레벨은 프로그램이 관리한다. 모델이 임의로 낮출 수 없어야 한다.
- 요약이나 변환만으로 보안 레벨을 자동으로 낮추지 않는다. 하향 조정은 별도의 명시적 정책·승인을 요구한다.
- 악의적인 내용을 완벽하게 탐지하는 것보다, 공격자가 허용 범위를 넘지 못하도록 하는 것이 목표이다.

* 임의 Bash 실행
- 임의 Bash 명령은 요청마다 생성하는 제한된 일회성 샌드박스에서 실행한다.
- 명령 문자열의 악의를 완벽하게 판별하려 하기보다, 악의적인 명령도 부여된 범위를 넘지 못하도록 제한한다.
- 샌드박스 권한은 모델이 아니라 코어가 결정한다.
- 기본 제한 방향:
  - 파일 접근은 명시적으로 제공한 범위로 한정하고, 가능하면 읽기 전용으로 제공한다.
  - 쓰기는 임시 작업 영역으로 제한한다.
  - 네트워크는 기본 차단하고, 필요한 경우에만 제한적으로 허용한다.
  - 호스트의 토큰, SSH 키, 환경 변수 등 자격 증명을 기본적으로 전달하지 않는다.
  - 실행 시간, 메모리, 프로세스 수, 출력 크기 등 자원 사용을 제한한다.
  - 종료 시 자식 프로세스까지 정리하고 환경을 폐기한다.
- 산출물을 호스트에 반영하는 행위는 별도의 정책 검사·승인 대상이다.
- 다음 실행으로 넘기는 파일과 결과는 환경 폐기와 별개로 정보 전달 정책을 적용한다.
- 실제 격리 기술은 미정이다. 임시 디렉터리나 컨테이너 생성만으로 보안 격리가 충족되었다고 간주하지 않는다.

* 보장 범위와 한계
- 모든 I/O 중재의 범위는 관리 대상 모델·Agent·도구가 수행하는 외부 접근이다.
- Cloud 제공자 내부의 동작까지 통제할 수는 없다. 우리가 전달하는 입력과 실행해 주는 요청을 통제한다.
- 로컬 모델과 도구가 코어를 우회하지 못하도록 OS 권한·샌드박스 등 실제 강제 수단이 필요하다.
- 허용된 목적지 외 접근을 막는 것이지, 서버의 악의성을 완벽하게 판별하는 것은 아니다.
- 내부 워크플로를 숨기는 것은 부가적인 방어일 뿐이며, 공격자가 구조를 알아도 권한 경계가 유지되어야 한다.
- 프롬프트 인젝션에 대한 완전한 면역을 주장하지 않는다. 응답 오염, 허용된 기능의 악용, 비용 소모 등은 별도 통제가 필요하다.
- 입력·출력 스키마, 데이터 전달 정책, 행동 권한, 실행 격리는 서로 보완하는 계층이다.

* 구현 방향과 현재 상태
- 구현 언어는 OCaml, 빌드 도구는 Dune을 사용한다.
- OCaml 타입과 모듈 인터페이스는 코어 구현의 안전성과 추상화에 활용한다.
- 사용자가 OCaml을 반드시 작성해야 하는 것은 아니다. 외부 스크립팅 인터페이스와 ABI 또는 IPC/RPC 제공 방식은 추후 결정한다.
- 현재 최소 구현:
  - ~Task~: 클로저 기반 지연 계산, ~create~, ~run~, ~map~, ~bind~
  - ~Agent~: 입력을 받아 Task를 생성하는 함수, ~create~, ~apply~, ~run~
  - 지연 실행, 결과 변환, Agent 간 순차 연결 테스트
- ~Task~ 의 실행은 현재 동기적이며 결과를 캐싱하지 않는다.
- ~return/pure~ 등은 실제 필요가 생길 때 추가한다.
- 기존 타입 중심 구상인 ~Agent[D, I, O]~, ~Effect[E, T]~, ~Secure[L, T]~, ~Trusted/Untrusted~ 는 확정된 API가 아니다. 실제 정책과 실행 경계의 필요에 따라 재검토한다.
- 핵심 로직과 설계 결정은 사용자가 직접 통제하며, 에이전트는 설명·검토와 명시적으로 요청한 보일러플레이트 작성을 지원한다.
